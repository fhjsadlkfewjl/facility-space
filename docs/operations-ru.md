# Обслуживание сервера

Настройка проверена 24 ноября 2026 года на VPS 2.29.173.184. Текущее состояние смотрите командами ниже.

## Что работает

- Полная копия PostgreSQL и файлов приложения каждые 6 часов: 00:30, 06:30, 12:30, 18:30 UTC, задержка до 30 секунд. Хранятся успешные копии за 14 дней.
- Вместе с копиями сохраняются образы текущих API, интерфейса, PostgreSQL и Caddy. Конфигурация содержит секреты: всё доступно только root, через сайт копии не выдаются.
- По воскресеньям в 03:30 UTC последняя копия восстанавливается в отдельном временном PostgreSQL. Проверяются содержимое всех таблиц и значения последовательностей. Тестовый контейнер и его данные удаляются.
- Каждые 5 минут проверяются контейнеры, чтение базы, HTTPS, отказ API без входа, срок сертификата, задачи резервирования/восстановления/сертификата, свободный диск и свежесть копий.
- Ошибки записываются в журнал systemd и статус на сервере. Доставка уведомлений человеку и внешний контроль доступности пока не подключены.
- Обновление сертификата каждые 6 часов уже было настроено; его конфигурация сохранена.

## Проверено

В отдельной копии восстановлены 32 таблицы, 59 365 записей. Их контрольные суммы совпали. Запущены текущие API и интерфейс; проверены доступ АХО, отказ без входа и повторный запуск сохранённых образов. Заведомо неисправный кандидат обновления отклонён. Тестовые контейнеры удалены. До и после проверки контрольные суммы всех рабочих таблиц и идентификаторы рабочих контейнеров совпали.

Каждый новый выпуск проверяется отдельно.

## Команды на сервере

```sh
# Сделать копию, проверить её восстановление, проверить запуск приложения на копии
sudo facility-ops backup
sudo facility-ops verify
sudo facility-ops rehearse

# Проверить состояние
sudo facility-ops monitor
sudo cat /var/lib/facility-ops/health-status.json
sudo systemctl list-timers 'facility-*'
sudo journalctl -u facility-backup -u facility-verify -u facility-monitor --since '24 hours ago'
```

Копии: `/var/lib/facility-ops/backups`. Образы: `/var/lib/facility-ops/releases`. Результаты: `backup-status.json`, `restore-status.json`, `rehearsal-status.json`, `acceptance.json`, `health-status.json` в `/var/lib/facility-ops`.

## Обновление и откат

Обычный выпуск из локального проекта: `bash scripts/update-staging.sh`. Он собирает кандидата отдельно от работающего приложения. На сервере обязательны резервная копия и запуск кандидата на восстановленной базе. Только после успешной проверки заменяются API и интерфейс. При неудаче запуска возвращаются предыдущие образы; рабочая база не восстанавливается поверх текущей и не очищается.

Ручной выпуск уже собранных образов:

```sh
sudo facility-ops update --api sha256:ПОЛНЫЙ_ID_API --web sha256:ПОЛНЫЙ_ID_WEB
sudo facility-ops rollback
```

Откат доступен после первого успешного выпуска через этот механизм. Проверить сохранённую текущую версию без переключения сайта: `sudo facility-ops checkpoint`.

**Изменения схемы базы и миграции, изменяющие данные, автоматически не выпускаются.** Проверка остановит такой выпуск до изменения рабочего сайта. Для него нужен отдельный план совместимости и возврата. Откат кода сохраняет все текущие данные; возврат базы к старой дате — отдельная аварийная операция с оценкой потерь.

Не запускайте старый ручной сценарий миграции или `docker compose down -v`. Не удаляйте каталог `releases` и сохранённые образы до проверки внешних копий.

## Восстановление при потере сервера

Нужны каталог успешной копии и соответствующий каталог releases из manifest.json. Проверить SHA256 файлов по manifest.json и images.sha256; загрузить образы через `docker load -i images.tar`. Конфигурацию из application.tar.gz распаковать на новый закрытый сервер. Базу восстанавливать через `pg_restore --exit-on-error` в новую пустую БД той же версии PostgreSQL, а не поверх рабочей. До открытия доступа проверить данные, запуск API, отказ без авторизации и HTTPS. Сертификат для нового адреса выпускается отдельно. Старую БД сохранять до принятия результата.

## Что ещё требуется

1. Регулярная копия вне VPS. Локальные копии не спасут при потере самого сервера.
2. Адресат уведомлений и независимая внешняя проверка: сам сервер не может сообщить о собственном полном отключении.
3. Ответственный за доступ и восстановление; согласовать допустимый промежуток потери данных (сейчас до 6 часов между копиями).
4. Для корпоративного запуска — персональный корпоративный вход и утверждённые права вместо текущих демонстрационных ролей; проверка актуальности данных с АХО.

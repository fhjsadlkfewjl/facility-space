# Facility Space: точная защищённая staging-копия

Подготовлено 15.11.2026. На удалённый сервер ничего не отправлено. Рабочая локальная база не изменена. Snapshot — согласованная копия на момент подготовки; последующие локальные изменения автоматически не синхронизируются.

## Что переносится

Исходная private-pilot-db → отдельная offline-копия → staging-data/snapshot.json → PostgreSQL 17. Повторного импорта, seed и обезличивания нет. Все прикладные таблицы сохраняются, включая сотрудников, подразделения, назначения, брони, историю, карантин и параметры объектов. Во время восстановления сравниваются полные содержимые таблиц и внешние ключи. Значения последовательностей сохраняются. Исключение: даты выполнения schema_migrations отражают установку новой базы; имена и контрольные суммы миграций обязаны совпасть.

- 15 зданий: 14 импортированных и существующее тестовое `aaaa`.
- 78 этажей: 58 активных импортированных, 19 неактивных импортированных и один существующий тестовый.
- 58 оригинальных SVG этажей, без изменений. Никаких fake SVG.
- 1 758 помещений, 4 670 объектов мебели, 39 шаблонов, 4 130 рабочих мест.
- 35 650 записей справочника сотрудников, включая существующую локальную демонстрационную учётную запись. Это не число действующих сотрудников.
- 2 357 записей назначений (включая историю), 4 бронирования, 3 216 записей аудита.
- 547 записей карантина остаются без изменений.
- Геометрия, координаты, углы, размеры, SVG мебели, площадь и классификация сохраняются в исходных строках.

Активные импортированные этажи по зданиям: АЛЬФА — 8, АСТРА — 10, Декабрист — 5, Декабрист 2 — 2, Вега — 1, С-КЛАССИК — 2, ФАКТУРА — 1, МОДУЛЬ — 5, СЕРВИС — 4, ТЕРРА — 9, Титул 7000 — 2, Титул 7300 — 5, Штаб 1 — 2, Штаб 2 — 2. Это ограниченная проверка, не гарантия отсутствия всех возможных персональных обозначений. SVG не редактировались.

## Защита и отличия от локального запуска

API и PostgreSQL не публикуют порты. Caddy по умолчанию слушает только 127.0.0.1 сервера. До настройки домена сайт открывается через SSH-туннель. Не публиковать IP как ссылку владельцу.

После настройки HTTPS используется существующий экран входа приложения: секретный токен с ролью. API требует его для доступа к офисным данным и SVG. HTML/JS экрана входа и `/health` доступны без входа; данных офиса или токена в JS нет. Это временный общий доступ владельца, не корпоративный SSO. Владелец общего токена может выбирать admin/facilities/employee: выдавать его только доверенному владельцу проекта.

Basic Auth поверх API не включён: он использует тот же Authorization, что и текущий вход приложения. Два конфликтующих механизма не накладываются. Вход приложения по HTTPS обеспечивает защиту данных. Существующий пользователь local-reviewer сохранён для поведения «моё место».

Не переносятся .env, секреты локального запуска, cookies, HAR, исходные SQL-дампы, сырая PGlite-директория, скриншоты. Поиск известных credential-полей и шаблонов токенов в snapshot не нашёл совпадений. Обычные корпоративные данные намеренно сохраняются по указанию владельца. Пакет содержит конфиденциальные данные: передавать только по SSH и не помещать в публичное хранилище.

Изменение browser localStorage (выбранный экран, масштаб, вход) между компьютерами автоматически не переносится. Код интерфейса и серверные данные сохраняются; на staging вход выполняется явно.

## Подготовка и перенос с Mac

Пакет создаётся только из разрешённого списка файлов. При повторной подготовке перенесите предыдущую staging-package в закрытую резервную папку: скрипт не перезаписывает её.

```sh
cd '/Users/miknrkn/Documents/ChatGPT/office map/facility-management'
python3 scripts/package-staging.py
ssh root@2.29.173.184 'install -d -m 700 /opt/facility-space'
rsync -az --exclude='.env.staging' --exclude='backups/' staging-package/ root@2.29.173.184:/opt/facility-space/
```

Пакет не содержит node_modules и готовых Mac-бинарников. Образы собираются на VPS под его архитектуру. Никаких изменений firewall эти команды не выполняют.

## Первый закрытый запуск на VPS

```sh
cd /opt/facility-space
bash scripts/staging-env.sh
bash scripts/deploy-staging.sh init
```

Секреты создаются на VPS в .env.staging с правами 0600, не печатаются. Init восстанавливает только пустую базу после миграций; при наличии прикладных данных отказывается работать. Восстановление выполняется транзакцией; справочник из 14 стандартных типов миграции заменяется точным справочником snapshot. На обычном старте seed не выполняется.

С Mac:

```sh
ssh -N -L 18080:127.0.0.1:80 root@2.29.173.184
```

Открыть http://localhost:18080. В отдельном SSH-сеансе посмотреть значение DEMO_TOKEN из .env.staging, не отправляя файл целиком и не публикуя секрет. В поле токена ввести значение с суффиксом `:admin` (или `:facilities`, `:employee`). Для смены роли выйти и войти снова. Передача владельцу — только отдельным закрытым каналом.

## HTTPS перед передачей ссылки

1. Выбрать домен и направить A-запись на 2.29.173.184; удалить неправильную AAAA-запись, если IPv6 не настроен.
2. На VPS изменить ТОЛЬКО `PUBLIC_ADDRESS=https://ваш-домен` и `HTTP_BIND=0.0.0.0` в .env.staging. Сохранить секреты.
3. Выполнить `bash scripts/deploy-staging.sh update`.
4. Проверить HTTPS, вход и отсутствие доступа к `/api/buildings` без токена (401). Проверить, что публичный IP не открывает приложение. Только затем передавать HTTPS-ссылку владельцу.

Caddy получает сертификат при доступном DNS и портах 80/443. До этого шага публичной ссылки на готовый staging нет. Подробности: https://caddyserver.com/docs/automatic-https

## Проверка и обслуживание

```sh
cd /opt/facility-space
docker compose --env-file .env.staging -f compose.staging.yaml ps
docker compose --env-file .env.staging -f compose.staging.yaml logs --tail=80 api caddy
```

Проверить вход, АЛЬФА/8, поиск знакомого сотрудника, рабочее место и АХО. Не использовать реальные назначения для случайных тестовых изменений: staging независим от локальной базы, но сохраняет исходные данные демонстрации.

Обновление кода: снова передать allowlisted пакет, затем `bash scripts/deploy-staging.sh update`. Перед изменением схемы скрипт делает pg_dump в закрытую backups/. Snapshot повторно не применяется. Данные PostgreSQL находятся в постоянном Docker volume. Никогда не запускать `down -v` для staging.

Резервная копия вручную:

```sh
umask 077
mkdir -p backups
docker compose --env-file .env.staging -f compose.staging.yaml exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/manual.dump
```

Проверка восстановления в ОТДЕЛЬНУЮ базу (имя должно быть свободным):

```sh
docker compose --env-file .env.staging -f compose.staging.yaml exec -T db sh -c 'createdb -U "$POSTGRES_USER" facility_restore_check'
docker compose --env-file .env.staging -f compose.staging.yaml exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d facility_restore_check --exit-on-error' < backups/manual.dump
```

Для отката сохранять предыдущий пакет кода и backup. Сначала восстановить backup в отдельную базу, проверить, затем переключить POSTGRES_DB на неё и запустить совместимый предыдущий код. Не выполнять слепой downgrade миграций и не затирать действующую базу.

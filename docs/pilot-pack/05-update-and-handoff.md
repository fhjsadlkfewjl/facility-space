# Обновить staging и передать IT

## После локальных изменений — на Mac

```bash
cd '/Users/miknrkn/Documents/ChatGPT/office map/facility-management'
bash scripts/update-staging.sh
```

Это действующий rsync/SSH-процесс, не git/CI. Команда проверена на VPS с выпуском `pilot-20261115T100116Z`.

Она выполняет сборку на Mac → загружает только разрешённые файлы кода в отдельную incoming-папку → проверяет контрольные суммы → сохраняет предыдущий код → собирает новые образы на VPS → ненадолго останавливает запись → делает pg_dump и проверяет читаемость архива → применяет миграции → запускает сервисы → проверяет HTTPS и 401 без входа. Каждый выпуск имеет отдельный IMAGE_TAG; tag записывается в серверную .env.staging только после успешного запуска.

**Не переносятся:** локальная база, staging-data, назначения, .env, ключи, сертификаты и Caddy/Compose-конфигурация сервера. Локальное изменение данных не появится на staging само. Не использовать старую полную staging-package для обычного обновления. Не запускать `init` повторно. Не запускать `down -v`.

На VPS вручную ничего выполнять не нужно, если Mac-команда закончилась `Updated ... HTTPS health OK; anonymous API denied`.

```bash
 curl -s -o /dev/null -w '%{http_code}\n' https://2.29.173.184/api/buildings
```

Ожидаются healthy у API/web/db, запущенный Caddy, `{"status":"ok"}`, затем `401`. Перед каждым показом пройти 8 пунктов smoke, а не полный QA.

## Если обновление завершилось ошибкой

Не запускать init/reset и не удалять volume. Лог команды показывает этап. Старый код: `/opt/facility-space/backups/pilot-...-code.tar.gz`; backup БД: `backups/before-update-....dump`; прежние Docker images сохранены. Ключи и сертификаты не затрагиваются.

При ошибке сборки база ещё не менялась. При ошибке запуска/миграций сначала посмотреть логи и состояние; не обещать автоматический rollback схемы. Если миграция уже успешно применилась, откат требует совместимого кода либо восстановления backup в отдельную базу. Передать ошибку вместе с именами выпуска и backup. Это небольшой staging helper, не отказоустойчивая CI/CD-система.

## Передача IT — одна встреча и один комплект

Дать: текущий исходный проект, этот pack, compose.staging.yaml, deploy/staging/, scripts/update-staging.sh и deploy-staging.sh, db/migrations, инструкцию HTTPS и отдельным закрытым каналом доступ к VPS/резервным копиям. Секреты не класть в презентационный ZIP.

Спросить у IT:
1. Где размещаем сервис и кто отвечает за него?
2. Как подключить корпоративный вход и какой постоянный ID сотрудника использовать?
3. Откуда и как часто получать сотрудников/подразделения, как учитывать увольнения?
4. Какие группы дают employee/АХО/admin и доступ к зданиям?
5. Где в Bitrix нужна ссылка и кто её видит?
6. Кто настраивает внешние backups, мониторинг и проверку восстановления перед production?

Спросить у АХО:
1. Кто принимает пилот и какие 8 задач считаем обязательными?
2. Кто отвечает за каждое здание?
3. Кто подтверждает площади, классификацию, масштаб и инвентарные номера?
4. Кто решает спорные назначения?
5. Нужны ли парковка/аренда/стоимость в первой очереди; если да — кто даёт реестры, договоры и тарифы?

Запуск не зависит от «закрыть все замечания качества». Он зависит от принятого набора сценариев, корректных прав, достоверности используемых данных и готовности эксплуатации.
